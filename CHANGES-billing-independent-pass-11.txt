B2  LOW-MED  Webhook audit rows recorded Paystack's IP as the actor's IP.
    logAudit() fills audit_log.ip_address from the ambient request's x-forwarded-for unless the actor is one of
    three hard-coded system emails. The webhook's audit() passes the CUSTOMER's email as actor, so every
    Paystack-driven row (payment_succeeded, payment_failed_*, plan_changed, refund/dispute, card_expiring) stored
    the provider's egress IP — a value the settings audit table, CSV and PDF present as the actor's IP and that
    request-ip.ts calls the field most likely to matter in a security investigation. Wrong is worse than empty.
    -> lib/utils/audit.ts: new optional `omitClientIp` param; an explicit ipAddress still wins; all other
       callers unchanged (portal routes legitimately record the external signer's IP).
    -> billing/webhook audit() sets omitClientIp: true.

B3  LOW  A re-run of charge.success could write a second "payment succeeded" line in Payment history.
    When completeWebhookEvent fails to record a finished event the claim stays 'processing'; a redelivery takes it
    over after STALE_CLAIM_MS and re-runs the handler. Every write is idempotent except the append-only audit
    insert (billing/history is built only from audit_log), so the same charge showed twice.
    -> webhook audit() takes `dedupeByReference`: before inserting, skip if a row with the same workspace, event
       type and metadata.reference already exists. Used for charge.success only (a charge reference is unique;
       refund.processed can legitimately repeat a reference for partial refunds, and invoice.payment_failed
       payloads carry no reliable reference). A failed lookup writes anyway.
