FIX (LOW / hygiene — missing explicit REVOKE, same class as migration 103's own
finding): guardian_check_attachments (migration 085) — private-bucket evidence-
file metadata (file names, sizes, storage paths for client-submitted Guardian
evidence) — was created with ENABLE ROW LEVEL SECURITY but never got the explicit
REVOKE ALL ... FROM PUBLIC, anon, authenticated that every other table created
after migration 068 received:
  - cron_run_history (075) — "same ownership model as cron_heartbeats / ops_alert_state"
  - platform_admin_audit_log (090)
  - billing_pending_subscription_cancels (094)
  - project_members_active, a VIEW (070/083) — retroactively locked down by 103
    itself, for this exact reason

Migration 068's one-off DO $$ sweep only revoked table privileges from
anon/authenticated for tables that existed AT THAT TIME; it also tried to cover
every table created afterward via ALTER DEFAULT PRIVILEGES, but that same
migration's own comment (and 103's) admits it "may silently no-op depending on
which role owns the schema defaults." Every other post-068 table got its own
belt-and-braces REVOKE for exactly that reason. guardian_check_attachments — created
chronologically between 075 and 090 — is the one table that never did, missed even
by 103's own dedicated hunt for this pattern.

Actual exposure: low. RLS enabled + zero policies already default-denies
SELECT/INSERT/UPDATE/DELETE for every non-owner role regardless of table-level
grants, and the file bytes themselves are only ever reachable through
service-role-issued signed URLs (app/api/guardian/checks/[id]/attachments/route.ts).
Fixed on principle, same severity class as 103's own finding, so this table now
matches every sibling's lockdown instead of being the one silent exception.

Fix: supabase/migrations/105_guardian_check_attachments_grant_lockdown.sql
  REVOKE ALL ON public.guardian_check_attachments FROM PUBLIC, anon, authenticated;

No app code changes. No data migration. Safe to run any time; idempotent
(a bare REVOKE on privileges that are already absent is a no-op).
