Bugs fixed
----------

B7-11 — canReadProject() never excluded a soft-deleted project.
  Every sibling route in this section (messages GET/POST, message edit/
  delete, members add/remove/available, the project PATCH/DELETE/GET
  itself) separately re-fetches the project scoped to `deleted_at is null`
  before trusting canReadProject() — but GET /api/projects/[id]/activity,
  GET .../messages/unread-count and POST .../messages/read call it alone,
  with no such re-fetch. Net effect: after a Draft/Intake project is
  deleted (DELETE /api/projects/[id] only soft-deletes; it does not touch
  project_members), its full audit/activity history stayed readable and its
  discussion read-cursor stayed writable via direct API call — by a
  VIEW_ALL_PROJECTS admin, or by a restricted member whose project_members
  row a delete never cleans up — even though the project 404s everywhere
  else, including its own detail page.
  lib/utils/project-access.ts: the VIEW_ALL_PROJECTS branch's own `projects`
  query now adds `.is('deleted_at', null)`. The restricted branch reads
  project_members_active (migration 070), which had no way to exclude a
  deleted project at all (it joins to `projects` only for workspace_id) —
  migration 083 adds `AND p.deleted_at IS NULL` to the view itself, which
  also correctly narrows every OTHER reader of "which projects can this
  restricted user reach" that already depended on this view (approvals
  list, SOW list, @mention resolution) — none of those should have surfaced
  a deleted project either, and none of them were excluding one before this.

B7-12 — no pagination guard on the core `projects` reads.
  The Dashboard's project query, the Projects list's project query, and
  GET /api/projects all did a plain, unbounded .select() against `projects`.
  PostgREST silently caps a plain select at 1000 rows (Supabase default) —
  this exact failure mode is why lib/utils/paginate.ts's fetchPaged() exists
  and is already used for the equivalent read in lib/reports/scope-health.ts
  and lib/reports/portfolio-data.ts, each throwing rather than let a
  truncated read pass as complete. It was never applied to these three.
  Since Complete/Archived projects never count against any plan's project
  limit (lib/utils/project-limit.ts), a workspace's total non-deleted
  project count is genuinely unbounded and can plausibly cross 1000 for a
  mature agency — at which point the Dashboard, the Projects list and
  GET /api/projects would each silently start losing projects with no
  error and no visible sign anything was wrong.
  All three now use fetchPaged with a 20,000-row cap (matching the Portfolio
  history cap) and throw with a clear message if that's ever exceeded,
  rather than truncate silently.

B7-13 — "At risk (pending COs)" undercounted: excluded 'expired' change
  orders.
  components/projects/ProjectDetail.tsx's `openCos` (the project header's
  at-risk tile) filtered to
  ['awaiting_response','countered','stalled','awaiting_countersignature'] —
  missing 'expired', even though the same file's own handleMarkComplete,
  the complete route's BLOCKING_CO_STATUSES, and lib/utils/attention.ts's
  actionableCoStatuses all already treat an expired CO (its signing link
  died with no answer given) as exactly as unresolved as a stalled one.
  Added 'expired' to the filter so this tile agrees with the rest of the
  product about what counts as still-pending exposure.

B8-7 — Portfolio PDF's "Documents needing action" had no row cap.
  lib/pdf/portfolio-report.tsx explicitly caps "Projects by risk" at 20 and
  "Exceptions" at 15, specifically to keep the PDF a short, readable
  summary (per that file's own comments) — but stuckDocs had no equivalent
  cap, and lib/reports/scope-health.ts returns every stalled / declined /
  expired / changes-requested / countered document workspace-wide with no
  limit parameter to cap it with in the first place. A workspace with a lot
  of history could render an unbounded number of rows here, against the
  export route's own 60-second timeout. Added a STALL_ROWS = 40 cap,
  matching the existing pattern (a "oldest N of total — the CSV export
  lists every one" header, same wording style as the flags/exceptions
  sections above it). stuckDocs already arrives oldest-first from
  scope-health.ts, so the cap keeps the most overdue items, same ordering
  intent as the CSV export (which stays uncapped — it's meant to be the
  complete record).
