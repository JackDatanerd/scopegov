FEATURE GAPS: none found in either section beyond what's listed below.

BUGS FIXED

1. app/(app)/projects/[id]/page.tsx — deactivated team members never disappeared
   The project's Team fetch was the one place in the codebase that joined
   workspace_members without `!inner` + `.eq('workspace_members.status','active')` —
   every other embed of this table (GET /api/projects, Dashboard, Projects list,
   /api/invoices, /api/search, /api/clients) filters to active members this way.
   project_members rows are never cleaned up when a member is deactivated, so a
   departed team member stayed permanently visible in the Team tab (name, email,
   avatar, working Remove button) — and the same unfiltered `team` array fed the
   Escalate-flag / Escalate-CO modals' dropdowns, offering a deactivated colleague
   as an escalation target (the API already rejected it server-side, but the
   dropdown shouldn't have offered them). Filtered at the source.

2. lib/utils/contract-value.ts — loadRetainerMonthsBilled silently truncated
   Used a single `.limit(5000)` per 100-project chunk with no truncation check,
   unlike every other big read in this area (fetchPaged, which throws on overflow
   specifically to avoid this). A chunk of long-running open-ended retainers
   averaging 50+ billed months each would silently undercount past 5,000 rows,
   understating "effective contract value" on both the Dashboard/Projects list and
   the Portfolio's scope-health numbers, with no signal anything was cut off. Now
   pages in full via .range() per chunk; a much higher safety cap remains (this
   function's own design degrades rather than throws), but hitting it is now
   logged loudly instead of silently swallowed.

3. app/api/projects/[id]/route.ts — narrow race on the SOW-lock for contractValue /
   retainerDurationMonths
   The three-way SOW lock (blocked once signed / while out for signature / while a
   draft has a pending approval) — the file's own "flagship finding" for
   retainerDurationMonths — was checked only against the project row read at the
   top of the handler, not re-verified at write time. A SOW signed, sent, or
   dropped into an approval chain in that gap could let a value/duration change
   slip through. Extracted the check into a shared checkSowLock() helper (used
   identically by both fields) and re-run it against a fresh read immediately
   before the write, mirroring the "re-check right before committing" shape
   already used for the plan-limit race in POST/reopen.

4. components/portfolio/PortfolioDashboard.tsx — hasSnapshots was dead
   getPortfolioData() computed and returned hasSnapshots, typed all the way into
   this component's props, but nothing ever read it — the dashboard, the CSV
   export, and the PDF export each independently derived "not enough history"
   from history.length alone. That's the right message for a genuinely new
   workspace, but misleading for a workspace that DOES have snapshot history
   where every point got filtered out of the risk chart because each day's
   dominant currency didn't match today's — "check back after a few daily
   rollups" implies waiting will fix it, when the real cause is a currency mix
   that may keep shifting. TrendChart now takes hasSnapshots and shows the
   correct message for each case.

5. lib/reports/period.ts / lib/reports/portfolio-data.ts — duplicated PERIOD_DAYS
   Defined identically (and, until now, only by luck kept in sync) in both files.
   Exported once from period.ts; portfolio-data.ts imports it instead of
   re-declaring it.

6. app/(app)/projects/page.tsx — trivial type-safety gap (found via tsc --noEmit,
   zero runtime impact)
   `restrictedIds = (ids || []).map(...)` was typed `any` (service is `as any`),
   so TypeScript couldn't narrow `restrictedIds` away from `string[] | null` on
   the very next line despite the assignment. Explicit cast added; behavior
   unchanged.
