!! v2 CORRECTION (supersedes the first HubSpot archive; apply THIS one — it contains every HubSpot file, whole)
While writing the setup guide I checked HubSpot's CURRENT docs and found two things my first version got wrong:
 1. OAuth v1 is deprecated. HubSpot retires /oauth/v1/token, /oauth/v1/access-tokens and /oauth/v1/refresh-tokens on 2027-02-16 (then they
    return errors) and my code used all three: it would have worked at launch and broken in ~3.5 months. Now: POST /oauth/2026-03/token
    (exchange + refresh), POST /oauth/2026-03/token/introspect (token in the BODY, with client credentials; the connect callback also
    refuses an `active:false` token), POST /oauth/2026-03/token/revoke on disconnect. Secrets and tokens are never in a URL (the newer API
    rejects that). Token errors are read from the standard `error` field as well as HubSpot's `status`. The test fake now answers 410 to any
    /oauth/v1/ call, and regression tests assert every OAuth call is 2026-03, POST, body-only; four mutants that restore the old calls are caught.
 2. The SCOPES: the authorize URL now also sends `oauth` (HubSpot's new apps declare it as a required scope and require every scope sent in the
    URL to be declared as required). A test parses the app-hsmeta.json example in integrations/hubspot/README.md and fails if its
    requiredScopes differ from the scopes the code sends.
 3. The SETUP in my first README was out of date: HubSpot disabled creating new "legacy public apps" in the UI (2026-05-26 new accounts /
    2026-06-23 existing); new apps are made with the Projects platform + CLI (`hs project create`, app-hsmeta.json). integrations/hubspot/README.md
    is rewritten, including the 25-INSTALL CAP on unlisted marketplace-distribution apps (customer #26 cannot connect until a Marketplace listing
    is approved) — plan for that if you expect many HubSpot customers.
Also updated from current docs: integrations/zapier (Node 22+, public listing is requested in the web UI, needs 3 users with a live Zap) and
integrations/google-drive (Google Auth Platform tabs: Branding / Audience / Data Access / Clients). Nothing else changed.
HubSpot CRM calls remain /crm/v3 and /crm/v4; HubSpot is moving to date-based API versions, so skim its changelog before launch.

DECISIONS MADE FOR YOU
- ONE-WAY (ScopeGov -> HubSpot). Two-way needs conflict rules and loop prevention, which is where CRM syncs go wrong; prove one-way first.
- NEVER OVERWRITE their CRM. An existing contact (same email) or company (same name, oldest) is LINKED to and left exactly as it is; only
  the deals ScopeGov created are ever edited. Nothing is ever deleted (disconnecting leaves everything in HubSpot).
- NO custom HubSpot properties, so no schema scopes. Idempotency lives in our own integration_external_refs; a deal created just before
  a crash is re-found by name + "created in the last hour".
- Deal pipeline = the account's default (chosen at connect, changeable); stages are found from HubSpot's own metadata (isClosed +
  probability), so custom stage ids work. A pipeline lacking Closed-won / Closed-lost is refused.
- PRIVACY: connecting needs VIEW_CLIENT_DATA (the sync shares client names, emails and phones); each event needs the same permission as
  everywhere else; the deal AMOUNT (contract value) is OFF by default and switching it on needs VIEW_FINANCIALS. Notes are escaped plain
  text. No contract values, emails or phone numbers go into notes or descriptions.

WHAT IT DOES (Pro and above)
  client (company name)  -> Company       client (email) -> Contact       project -> Deal (associated to both)
  SOW signed -> deal Closed-won (+ closedate)    SOW declined -> Closed-lost    change order accepted -> note (+ refreshed amount if enabled)
  scope flag raised / payment received -> note on the deal timeline
  Settings -> Integrations -> HubSpot: connect, portal, deals synced, event toggles, pipeline picker, amounts switch, "Sync existing
  projects", on/off, disconnect / reconnect. This removes the last "Coming soon" row (only Zapier's marketplace-listing status remains).

HOW
- Same pattern as Slack/Drive: a connection (encrypted refresh token; access tokens, ~30 min, are minted on demand) + ONE rule per
  connection (kind 'hubspot', config {pipeline_id, include_amounts}); queueing, retries, plan gate, lapsed handling, the 10-failure auto-
  disable and the cron are shared. delivery.ts gains a HubSpot branch on the same settle().
- lib/integrations/hubspot-sync.ts is the engine; external-refs.ts is a small shared helper (find/save/drop) for it.
- Self-healing: a 404 on a remembered deal/company/contact drops that record and rebuilds it (up to three heals in one run, since all
  three may have been deleted). Found while testing: a fresh company/contact is now ALWAYS re-associated to an existing deal.
- Outcome mapping: revoked / MISSING_SCOPES / 401 -> connection flagged, rules off, "Reconnect"; pipeline or stage rejected -> rule off with
  the fix; 429 / 5xx / 409 / timeouts -> retry; a problem with ONE project (deleted, nothing to link) -> dead for that delivery only, never
  counted toward auto-disable.
- Only https://api.hubapi.com/crm|oauth is ever contacted (allow-list enforced before any fetch). The shared OAuth-state module serves
  Slack, Google and HubSpot; a state minted for one is rejected by the others.
- Connect verifies every scope was granted (else revokes and says so) and reads the deal pipelines, so a setup problem shows immediately.
- Migration 171: kind 'hubspot' (no signing secret, needs a connection, one rule per connection); ref types company/contact/deal/note;
  an index so the nightly cleanup can prune note refs (30 days).
