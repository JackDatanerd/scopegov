BUGS FIXED (both mine, from round 1)
1. De-dupe dropped real events. Almost every notification is raised against the PROJECT (21 of 29 call sites use
   entityType 'project'), and 165 de-duplicated on (workspace, event type, entity id) for 10 minutes, so a second invoice
   paid / second Guardian flag on the same project inside ten minutes was silently lost. Now keyed on what the event SAYS
   (type, entity, title, summary; md5 in SQL, migration 166). Verified on real Postgres: two different payments -> both stored;
   identical announcement twice -> one; no key -> never de-duplicated.
2. Privilege bypass. Anyone with MANAGE_WORKSPACE_SETTINGS could subscribe a webhook to invoice/payment events (amounts in
   the text) or Guardian flags without holding VIEW_FINANCIALS / APPROVE_FLAGS. Subscribing now requires the permission the
   matching notification is raised under (lib/integrations/events.ts permissionForEvent; a test reads every
   notifyMembersWithPermission call site so the map cannot drift). Zapier: checked against the API key creator's CURRENT
   permissions (a removed/demoted creator's key stops being able to subscribe).

HARDENING
- lib/integrations/pinned-request.ts replaces safeFetch for deliveries: resolves ALL addresses, refuses if ANY is
  private/reserved (the old check looked only at the first record of a multi-A name), connects to the exact validated address
  (closes DNS rebinding), never follows redirects (3xx = permanent failure, no 8 pointless retries), one deadline for
  connect+TLS+headers. Real-socket tests prove the connection goes to the pinned IP (the hostname resolves nowhere).
  safe-fetch.ts: isBlockedAddress is now exported (no behaviour change).

NEW: ZAPIER
- app/api/integrations/v1/hooks (POST subscribe, idempotent on target URL), hooks/[id] (DELETE, idempotent, scoped to the
  key's workspace and to kind=zapier), events/[type]/sample, me. Hook URL pinned to https://hooks.zapier.com/hooks/…;
  100 Zap triggers per workspace; customer webhooks keep their cap of 10 (counted by kind).
- lib/integrations/event-catalog.ts (labels, descriptions, samples) + scripts/gen-zapier-events.mjs ->
  integrations/zapier/events.json (a test fails if it drifts) + integrations/zapier/{index.js,package.json,README.md}:
  19 REST-hook triggers, API-key auth.
- Settings → Integrations: Zaps listed separately (turn off / remove), Zapier row now says "App listing pending".
- Webhook PATCH on a Zapier row can only toggle it; "send test" is customer webhooks only.
- Payloads now carry project {id,name,status} and client {id,name} (names only; never contract value, email, phone).

VERIFICATION
- tsc clean; full vitest suite; real `next build`; migrations 165+166 applied twice on Postgres 16 with behaviour checks.
- Zapier's own validator (`zapier-platform validate`): "structurally sound". Its second, style pass needs Zapier's servers
  (unreachable from my sandbox) — NOT run.
- Zapier's runtime (createAppTester) driven against the real route handlers over HTTP: auth, wrong-key error, subscribe,
  perform, performList, refusal beyond permissions, unsubscribe — all pass (a throwaway harness, not committed).
- Pinned TLS: real HTTPS via the pinned address works. NOT demonstrated: that a wrong-hostname certificate is rejected —
  my sandbox's egress proxy re-signs TLS for any name, so the check cannot fail there. It rests on Node verifying against
  the request hostname (documented behaviour); worth one manual check from a normal machine.

KNOWN LIMITS
1. Payloads carry the notification's title/summary plus project/client names; document-level fields (invoice number,
   amount, SOW number) are NOT structured yet, because most call sites raise the notification against the project. Next:
   an optional `integrationData` on notify calls, wired per event. This is the biggest gap for Zapier usefulness.
2. A webhook keeps delivering if its creator is later demoted (Zapier hooks are checked only when subscribing too).
3. consecutive_failures is read-modify-write (two dead deliveries in one run can count as one).
4. Events raised through notifyUsers (approval_requested, escalation) are not announced.
5. Zapier app is NOT published: needs your developer account (register, push, promote, review).
