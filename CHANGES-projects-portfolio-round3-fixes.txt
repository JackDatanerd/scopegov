SECTION 7 — Projects & Dashboard
---------------------------------
1. components/projects/ProjectDetail.tsx — TeamTab's openAddModal()
   Was the only action in the file that never checked res.ok. A failed fetch of
   GET /api/projects/[id]/members/available (permission race, transient 500, network
   error) still opened the "Add member" modal and, with json.members undefined, showed
   "All workspace members are already on this project" instead of an error. A non-JSON
   error body also threw with no catch (unhandled rejection).
   Fix: now checks res.ok, surfaces a real error via addError (rendered both inside and
   outside the modal, since a failed load never opens it), and no longer opens the modal
   on failure. Mirrors the addMember/removeMember pattern already in this file.

2. components/projects/ProjectDetail.tsx — GenerateSowModal's revision-rounds input
   Had min={1} max={5}, but the AI-brief-parse acceptance logic right above it, and
   api/sow/generate's own server-side validation, both treat 1-10 as valid — a leftover
   from the round-17 SOW-lifecycle fix, whose own comment claimed this input "actually
   supports" 1-10 without the max attribute ever being updated to match.
   Fix: max raised to 10 to match what the field (and server) actually accept.

Feature gaps: none found in this section on this pass.

3. app/api/co/[id]/route.ts — existingAdjustmentIds Set<unknown> vs Set<string>
   `co` comes through a query cast to `as any`, so `new Set(...)` built from its
   line_items inferred as Set<unknown> instead of Set<string> — computeCoTotals's typed
   signature (ReadonlySet<string> | readonly string[]) then correctly rejected it,
   failing `next build` (and `tsc --noEmit`) entirely. The values themselves were always
   real strings; only the inference was wrong.
   Fix: `new Set<string>(...)` — explicit generic, no behavior change.

4. lib/ai/sow-content.ts — conflictingRoundCount()
   `for (const m of text.matchAll(...))` — TS2802, needs --downlevelIteration at this
   tsconfig's target. Same pattern already fixed elsewhere in round 17.
   Fix: wrapped in Array.from(...).

5. lib/approvals/pick-workflow.ts — same TS2802 pattern via `[...bestPerCurrency.values()]`.
   Fix: Array.from(bestPerCurrency.values()) instead of spread.

Without 3-5, `next build` fails outright — nothing in the app ships until they're in,
regardless of section 7/8 status. All three are typecheck-only fixes; no runtime
behavior changes.
