SECTION 14 — BUGS FIXED (found during a from-scratch section-13/14 re-audit; not yet present in
any prior CHANGES file for this repo)

 1. merge_clients() (077; cc_emails handling touched again by 086/087) moved EVERY one of the
    source client's client_contacts rows onto the target with no count check at all — unlike
    cc_emails, which has been capped at MAX_CC_EMAILS (10) since 086, client_contacts has an
    equivalent, already-enforced app-level cap (MAX_CONTACTS_PER_CLIENT = 25,
    app/api/clients/[id]/contacts/route.ts) that this function has bypassed since it was written.
    Two clients with 20 contacts each merged into one with 40 — silently past a limit POST
    /contacts itself refuses to cross by hand.

    089 caps this: it computes how much room is left under 25 on the TARGET before moving
    anything, and moves only that many of the source's eligible (non-duplicate-email) contacts,
    prioritising the ones that actually do something — the primary contact first, then role-typed
    (billing/scope/approver) contacts, then oldest first. Contacts that don't fit are left on the
    source row and cascade-delete with it when the source client is deleted at the end of the
    function — the same fate duplicate-email contacts already had, just a second reason it can now
    apply. The count left behind comes back as `contacts_dropped`.

    app/api/clients/[id]/merge/route.ts now passes `contacts_dropped` through to the response and
    into the audit row's metadata (alongside the existing `contacts_moved`). ClientDangerZone.tsx
    surfaces it with a plain alert() after a successful merge (this component already uses
    window.confirm/window.alert throughout, so this matches its existing style) rather than the
    loss being silent — the merge confirmation dialog's copy was also softened from "contacts...
    move" to "as many contacts... as fit", since the earlier wording promised something the
    function couldn't actually guarantee.

 2. Moved contacts are always demoted (is_primary = false) so they can never collide with the
    target's own primary slot — correct when the target already has one, but if the target had NO
    primary contact of its own, the merge silently left it with zero: the source's primary contact
    — the one signal lib/utils/client-contacts.ts's withPrimaryContactCc() actually uses for CC
    routing on every invoice/SOW/CO, independent of the cap in #1 — stopped being CC'd on anything
    for that client going forward, with nothing anywhere (not the merge dialog, not the result)
    saying so.

    089 fixes this: if the source had a primary contact AND it made it across (wasn't skipped as a
    duplicate email or dropped by the #1 cap) AND the target ends up with no primary contact at
    all, its primary flag is restored on the target. This never overrides a primary the target
    already had of its own.

Nothing else in merge_clients() changes: the projects move, the case-insensitive cc_emails
de-dup/cap (087), and the concatenation precedence are all untouched.

TESTS: no JS-level test exists for merge_clients() itself (it's a DB RPC with no harness here to
run it against — see every prior round's same caveat); the SQL was hand-reviewed for brace/CTE
correctness (LIMIT 0 on the eligible CTE when the target is already at/over the cap correctly
moves nothing rather than erroring, GET DIAGNOSTICS after an UPDATE...FROM still reports the
right row count, and the dropped-count query re-scans AFTER the move so it can't double-count a
row that already migrated to the target).
